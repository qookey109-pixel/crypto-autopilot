## Public-market adapter
The adapter intersects the curated crypto-only pool in `config/crypto_universe_v0_1.json` with live Pionex symbols and current valid quotes, then applies the existing spread/liquidity rules with a five-market bound. It requests 240 closed hourly bars only, rejects holdout-overlapping request windows before I/O, and rejects missing, duplicate, stale, nonfinite or out-of-window returns. A caller-supplied budget check runs before every request. No source fallback or historical acquisition is added.

Technical features, opportunity scoring and strategy routing reuse the existing implementations. The adapter emits source/time/hash evidence and a per-market `decision_trace` that joins candle-input status, opportunity evaluation, research-only route outcome and the explicit fact that execution selection was not performed. When macro context is unavailable, each scanned asset records `NOT_EVALUATED_REGIME_UNAVAILABLE`; it does not invent a neutral regime or alter the gate. This is report-only and does not itself submit orders or write R2.

### Pionex API key and market-context clarification

A Pionex API key is not needed for public market-data endpoints; the official API documentation distinguishes public market data from signed private endpoints. The Cloud Paper adapter currently requests public symbols, perpetual tickers, book tickers and closed 60-minute candles. The shared low-level client also has public methods for funding observations, derivative indexes, open interest and recent trades, but the Cloud Paper market-capture interface does not currently consume the first three. None of those per-contract fields supplies canonical TOTAL3, BTC dominance or aligned market-wide breadth. The missing `REGIME_UNAVAILABLE` context is therefore not caused by a missing user API key. The prior one-shot external context authority has expired, network capture remains closed, and private exchange API access remains unauthorized; do not request or add credentials as a workaround.

## Persistent coordinator primitive

The cloud step adapter lists the append-only slot, claim, run-step, and state namespaces before each new slot, checks exact coverage counts, and deeply verifies the latest committed report plus its direct predecessor. This keeps recovery checks bounded as history grows. Cash genesis is allowed only when all four namespaces are empty. Orphan claims/state, incomplete listings, missing steps, broken latest links, and stale caller predecessors stop before market requests. Replays return the existing verified report with zero market calls. With the approved strategy registry empty, production candidate injection is rejected and the valid no-trade path is exercised in CI. Reports now expose additive `reason_codes` that distinguish market review, unavailable regime/context, an empty eligible-strategy registry, and no qualified candidate; this changes reporting only, not candidate or risk decisions. This adapter is not connected to an Actions schedule or R2 credentials; full live-frame completeness and controlled activation remain outstanding. The Dashboard projection is merged and deployed, but it still reports no official Cloud Paper run or per-market trace. ## Budget reservation primitive

`src/crypto_autopilot/paper/cloud_budget_v0_1.py` validates account-wide usage evidence timestamps, measured-through freshness, complete reservation coverage, monthly/daily/rolling-31-day operation ceilings, object/run/day byte ceilings and the 8 GB storage hard stop before allowing a provider or R2 reservation. Synthetic tests cover stale, missing, incomplete, negative, over-limit and successful reservations. PR #547 also closes a boundary bug: in-run Class A/B reservations now count toward monthly limits, with regression coverage for the last remaining monthly slot.

The additive `BudgetedR2Store` adapter provides the interface used by `R2PaperRunStore` and wraps every individual Class A write/list-page request and Class B read with a pre-access reservation callback. Conditional writes pass through its client proxy. Its `from_credentials` factory sets zero SDK retries so one reservation cannot silently expand into hidden retry attempts; the existing shared `R2Store` implementation and frozen V0.10 critical paths remain untouched. The budget guard exposes a callback-compatible dispatcher, and the Pionex adapters already accept pre-request callbacks. Synthetic CI checks verify reservations happen before I/O.

This is still adapter support, not production wiring. The Cloud Paper workflow, Cloudflare usage collector, production-wired account-wide reservation ledger, and complete coverage of unrelated account writers are absent. Shared-account usage evidence remains missing; no deployment, controlled main acceptance, provider/R2 operation, or natural schedule is authorized by this change.

## Atomic D1 reservation ledger (prepare only)

PR #549 merged at `439054a940950b9bd564a1c93026e206f0b55b84` adds a D1-backed atomic slot reservation adapter and a prepare-only SQL migration. It reserves the full per-run envelope once before provider/R2 access, accounts for unsettled and settled reservations made after the snapshot coverage boundary, and settles only measured usage. An unknown write/readback outcome remains reserved and requires review; it is not retried or released automatically.

This is implementation groundwork only. It does not provision or migrate a production database, create secrets, collect shared-account R2 usage, cover unrelated account writers, call Pionex, access R2, or enable an Actions workflow. A complete account-wide reservation inventory and independently verified current usage evidence are still required before the account can be treated as covered. Any D1 free-tier quota is a separate usage boundary and must also be shown to remain within the project’s 0 USD policy before activation. The pending_* values supplied alongside a snapshot must represent reservations outside this D1 ledger only; ledger reservations are aggregated from D1 itself.
